# ISO/IEC 27001 與 ISO 9001 導入規劃

驗證的對象是公司的管理系統，不是這套程式。程式碼不會「通過」或「不通過」ISO，
它的角色是提供證據。以工作量估計，八成落在文件與紀錄，兩成落在程式。

## 合併成一套管理系統

兩份標準同屬 Annex SL 高階架構，第 4 章到第 10 章的骨架相同。分開建置等於把同一份
文件寫兩次，也會出現兩套互相矛盾的稽核紀錄。共用文件約占全部強制文件的七成，並可
向驗證機構申請合併稽核（combined audit）。

共用：驗證範圍、管理系統政策、目標與達成規劃、人員能力與訓練紀錄、內部稽核計畫與
結果、管理審查紀錄、不符合事項與矯正措施紀錄。

27001 專有：風險評鑑方法與評鑑結果、風險處理計畫、適用性聲明（SoA，附錄 A 共 93 條
逐條說明採用或排除）、監控與量測結果。

9001 專有：8.3 設計與開發管制（對軟體公司等於開發流程本身）、8.4 外部提供者評估、
8.7 不符合輸出的處置、9.1.2 顧客滿意度。

## 程式端的四個缺口（已完成）

1. **登入與登出進稽核紀錄**（A.8.15）。`auth::write_auth_audit` 為登入成功、登入失敗、
   登出與變更密碼各寫一列；初始化沿用原有的 `bootstrap_install`。回應對「查無此帳號」
   與「密碼不正確」仍是同一句，稽核紀錄則分開寫。被速率限制擋下的嘗試不寫——那一段還
   沒驗任何憑證。

2. **保存期限與匯出**（A.8.15、A.5.34）。`audit_keep_days` 預設 1825 天（五年），留空
   等於永久保存；伺服器每日清一次，改了不必重啟。匯出走 `list_ai_audit` 本身：多了
   `from`／`to` 與最高 10000 筆，畫面把取回的列組成 CSV 下載。

3. **來源位址**（A.8.15、A.8.16）。`ai_audit_log.client_ip` 取自前置代理的
   `X-Forwarded-For`，由伺服器解析成位址才寫入，不是位址就留空。只記錄，不參與判斷。

4. **相依套件弱點掃描**（A.8.8）。CI 加入 `cargo audit` 與 `npm audit --omit=dev
   --audit-level=high`，執行紀錄本身就是稽核要的證據。

刻意不做：稽核紀錄的雜湊鏈與唯寫儲存（要有人定期驗證才有意義，否則只是多一欄沒人看
的數字），以及自建的合規管理模組（把顧問的試算表換成一套要自己維護的軟體，而驗證
機構收的是紀錄不是介面）。

## 時程

第二階段稽核之前，管理系統必須已經實際運行一段時間，並且完整跑過一輪內部稽核與一次
管理審查。紀錄無法補寫，這是時程壓不下去的原因。

| 期間 | 事項 |
| --- | --- |
| 第 1 月 | 定範圍、接觸顧問與驗證機構、確定風險評鑑方法 |
| 第 2–3 月 | 管理系統手冊、風險評鑑與處理計畫、適用性聲明；同時完成上述四個程式缺口 |
| 第 4–6 月 | 依文件實際運行並累積紀錄，至少三個月 |
| 第 6 月 | 內部稽核與管理審查各一輪，留下不符合事項與矯正措施紀錄 |
| 第 7 月 | 第一階段稽核（文件審查），結果是一份待改善清單 |
| 第 8 月 | 第二階段稽核（實地稽核），查的是紀錄與實際執行是否相符 |
| 往後每年 | 監督稽核；第三年重新驗證，範圍與第二階段相當 |

## 費用概估

以台灣二十人以下、單一營運據點估算，幣別新臺幣。

| 項目 | 金額 |
| --- | --- |
| 輔導顧問（兩套標準併行） | 20–50 萬 |
| 驗證機構首次驗證，每套標準 | 15–30 萬 |
| 合併稽核可省 | 約 3 成 |
| 年度監督稽核，每年 | 首次驗證的 3–4 成 |

實際報價依人數、據點數與範圍大小變動，向兩到三家驗證機構詢價再比較。台灣常見的驗證
機構包括 BSI、SGS、TÜV、DNV 與台灣德國萊因，選擇時確認其驗證資格經 TAF 認可。

## 下一步

把驗證範圍寫成一句話，例如「Laysi One 財務與人資系統之開發、維運與客戶支援」。範圍
決定風險評鑑要涵蓋什麼、適用性聲明能排除哪幾條，也是每一家驗證機構報價的第一個問題。
這一句沒定案之前，其餘工作都會返工。
